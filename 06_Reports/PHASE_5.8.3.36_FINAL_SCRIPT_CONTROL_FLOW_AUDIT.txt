4. EXPLANATION OF SQLCMD ERROR TERMINATION & BATCH BEHAVIOR
================================================================================
A critical review requirement is evaluating whether ':on error exit', 'RETURN',
or 'SET NOEXEC ON' are individually sufficient or why all three are required.

1. SQLCMD Preprocessor Behavior (:on error exit):
   - Scope: Client-side command line utility ('sqlcmd.exe').
   - Behavior: When ':on error exit' is set, any error of severity 11 or higher
     (or undefined variable reference) causes sqlcmd to terminate immediately,
     refuse to send subsequent batches to the server, and return exit code 1.
   - Limitation: SSMS (SQL Server Management Studio) does NOT terminate the GUI
     process when ':on error exit' is encountered; SSMS parses SQLCMD directives
     client-side but continues processing subsequent batches across 'GO' delimiters
     unless instructed otherwise.

2. T-SQL Batch Control Flow (RETURN):
   - Scope: Server-side execution of the CURRENT batch only.
   - Behavior: 'RETURN' immediately halts execution of the statements following it
     within the same batch (up to the next 'GO' delimiter).
   - Limitation: 'RETURN' has ZERO effect on subsequent batches separated by 'GO'.
     If batch 1 raises an error and executes 'RETURN', the client application will
     still submit batch 2, and SQL Server will execute batch 2 normally unless
     a session-level suppression is engaged.

3. Session-Level Engine Setting (SET NOEXEC ON):
   - Scope: Server-side execution across the ENTIRE database session/connection.
   - Behavior: Once 'SET NOEXEC ON' executes, SQL Server places the connection into
     a mode where all subsequent statements across ANY batch are compiled for syntax
     validation but are NEVER executed. Zero DDL, zero DML, and zero state mutations
     take place.
   - Interaction: In SSMS GUI mode, if a precondition fails in Batch 4, 'RETURN' halts
     Batch 4, and 'SET NOEXEC ON' guarantees that Batches 11, 13, and 15 (containing
     CREATE DATABASE, CREATE LOGIN, CREATE USER) are compiled only and NEVER executed.

Synergistic Protection:
  - In CLI (sqlcmd.exe): ':on error exit' provides instant process abort (exit code 1).
  - In SSMS GUI: 'SET NOEXEC ON' provides session-level compile-only lock, while
    'RETURN' halts the failing batch immediately.
  Together, they establish a truly fail-closed, multi-environment control-flow defense.

6. CREDENTIAL-HANDLING LIMITATIONS & CORRECTED GUIDANCE
================================================================================
In accordance with review instructions 6 and 7, all overbroad claims regarding
"zero disk footprint" or "eliminated secret exposure" have been corrected in
05_Development/database/HSWRMS_TEST_PROVISIONING_GUIDE.md.

1. Clarification of SSMS Unsaved Query Tab (Section 2.B):
   - Claim Corrected: Removed claim that an unsaved query tab "guarantees zero disk footprint".
   - Risk Reduction Documentation:
     Using an unsaved query tab and closing it without saving provides SUBSTANTIAL
     RISK REDUCTION:
       a) It prevents the password from being written to a committed repository file.
       b) It eliminates git diff contamination.
       c) It avoids command-line argument exposure in process listings (Task Manager,
          Get-Process, Event 4688) and shell history files (ConsoleHost_history.txt).
     However, it is NOT an absolute guarantee of zero disk footprint because:
       * SSMS AutoRecover periodically creates temporary backup recovery files
         on disk (%USERPROFILE%\Documents\SQL Server Management Studio\Backup Files\).
         While closing without saving deletes this snapshot, data may reside temporarily
         on storage or in volume shadow copies.
       * OS Virtual Memory Paging (pagefile.sys or hiberfil.sys) can write SSMS process
         RAM to disk under memory pressure or hibernation.
       * Windows Clipboard History (Win+V) may retain copied passwords unless cleared.
       * Crash/Memory Dumps capture process RAM to disk upon abnormal termination.
   - Recommended Procedure: Keep the unsaved tab open only for the moments necessary
     to execute, close immediately with "Don't Save", and clear the clipboard.

2. Realistic Limitations of SecureString & Process Environment Variables (Section 2.C):
   - Claim Corrected: Documented that SecureString and process-scoped environment
     variables do NOT eliminate all secret exposure.
   - Realistic Limitations:
     * .NET CLR Heap: When unprotecting a SecureString via PtrToStringBSTR to pass to
       CLI processes, an immutable managed System.String is allocated on the .NET
       garbage-collected heap. In .NET, managed strings cannot be explicitly zeroed;
       they persist in RAM until garbage collection reclaims and overwrites the page.
     * Process Environment Inheritance: Storing the secret in $env:TEST_PASSWORD puts
       plaintext into the process environment block. Any child process spawned from
       that shell session inherits the environment block. Local administrators and
       tools running under the same user token can inspect the environment block.
     * Virtual Memory Paging: PowerShell process memory can be swapped to pagefile.sys.
   - Recommended Procedure: The simplest safe local procedure that avoids command-line
     exposure and persistent repository files is:
       Primary: Interactive SSMS in an unsaved tab with SQLCMD mode (Method 1).
       CLI Alternative: Ephemeral PowerShell environment variable with immediate nullification
                        ($env:TEST_PASSWORD = $null) and variable removal (Method 2).
