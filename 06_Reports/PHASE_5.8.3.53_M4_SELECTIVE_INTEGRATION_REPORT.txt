[Candidate A: M1/M2 Boundary Interfaces]
  - Workspace B Artifacts:
      * DietaryProfilePort.java

      * DefaultBookingAndDietaryIntegrationService.java
  - Evaluation:
      Workspace B implemented interface ports to decouple M4 from direct entity
      coupling with M1 (Dietary) and M2 (Booking).
      However, Workspace B's implementation contained critical flaws:
        1) Fallback to fabricated data: If booking was null, it defaulted to
           bookingId=1, room="Villa #102", guest="Eleanor Vance", package="RET-DETOX-03".
        2) Date fudging: Rolled expired checkouts forward to today + 14 days.
        3) Modulo guessing: Assigned package plans via (bookingId % 8).
        4) Violation of clinical data minimization: Exposing raw entities or
           potential health diagnoses instead of strictly dietary restrictions.
      Decision:
        ADOPT the architectural Port design, but REJECT all mock/fake fallback logic.
        Implement a clean, production-grade adapter querying authoritative M1/M2
        entities with strict null checks, date validation, and privacy filtering.

[Candidate B: Retreat Package F&B Plans]
  - Workspace B Artifacts:
      * RetreatPackageFnbPlanResponse.java
      * RetreatPackageFnbService.java
      * RetreatPackageFnbController.java
  - Evaluation:
      Workspace B hardcoded exactly 8 package codes ("RET-DETOX-03", "RET-MOM-03",
      "RET-SENIOR-03", "RET-STRESS-03", "RET-DIGEST-03", "RET-POSTSURG-03",
      "RET-DIABETES-03", "RET-REJUV-03") into an in-memory Map. During meal ordering,
      it validated item titles against allowed categories using substring keyword
      checks (e.g. item title contains "DETOX").
      Workspace A's authoritative package model is database-driven via M2's

      hardcoded rules would break real guest bookings that do not match the 8 codes,

4. CANDIDATE CHANGES DELIBERATELY REJECTED AND WHY
================================================================================
The following Workspace B implementations were examined and explicitly rejected:

1. Folio Billing in PENDING State:
   - Rejected: Workspace B triggers Folio billing prematurely when an order is created
     in `PENDING`.
   - Reason: Violates Approved Business Rule #1 ("A-la-carte charges are posted to the
     M5 Folio only when the order transitions to DELIVERED").

2. Swallowing Folio Billing Exceptions:
   - Rejected: Workspace B's `FolioBillingListener` catches and swallows billing errors,
     logging a warning and leaving the order in an inconsistent state.
   - Reason: Violates atomic transactional integrity between M4 and M5.

3. DELIVERED -> CANCELLED State Transition:
   - Rejected: Workspace B allowed orders in `DELIVERED` status to transition to `CANCELLED`.
   - Reason: Violates Approved Business Rule #5 ("DELIVERED is terminal and cannot transition
     to CANCELLED").

4. Omission of Persistent Cancellation Audit Records:
   - Rejected: Workspace B did not record cancellation reasons in `dbo.AuditLog`.
   - Reason: Workspace A's Phase 5.8.3.52 established durable audit trail logging via
     `AuditLogService` with action `CANCEL_MEAL_ORDER`.

5. Role-Only Permission Bypass:
   - Rejected: Workspace B used raw `@PreAuthorize("hasRole('FNB_STAFF')")`, bypassing
     the S39 permission catalog.
   - Reason: Violates Approved Business Rule #7 and S39 granular authorization standards.

6. Hardcoded 8 Package Restriction Engine:
   - Rejected: Workspace B `RetreatPackageFnbService` hardcoded 8 package plans.
   - Reason: Disconnects F&B from M2's dynamic database `dbo.RetreatPackage` and rejects
     legitimate resort bookings with custom or standard package identifiers.

7. Database Migrations V006 / V007 & FEFO Ingredient Deduction:
   - Rejected: Workspace B introduced `dbo.Ingredient`, `dbo.IngredientBatch`, and
     `dbo.MenuItemIngredient` with FEFO inventory logic.
   - Reason: Violates Mandatory Safety Constraint (zero SQL DDL/migrations) and Approved
     Business Rule #6 (batch deduction and FEFO are explicitly out of scope).
