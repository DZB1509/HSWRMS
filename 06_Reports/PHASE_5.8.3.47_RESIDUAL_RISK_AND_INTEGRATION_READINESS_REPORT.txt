5. SQL SERVER E2E PREREQUISITES & VERIFICATION GAPS
================================================================================

5.1 Verification Gaps (Unproven on SQL Server):
Because all automated integration tests run against H2 in-memory, the following technical behaviors remain unverified against Microsoft SQL Server:
1. Collation & Case Sensitivity: Vietnamese Unicode characters (NVARCHAR) handling and collation sensitivity (`SQL_Latin1_General_CP1_CI_AS` vs `Vietnamese_CI_AS`).
2. Concurrency & Locking Semantics: H2 uses MVCC snapshotting by default. SQL Server uses row/page shared locks for READ COMMITTED unless Read Committed Snapshot Isolation (RCSI) is enabled. Deadlock detection (Error 1205) and retry behavior under concurrent pessimistic write locking (`WITH (UPDLOCK, ROWLOCK)`) have not been tested on real SQL Server.
3. Temporal Datatypes: Precision and offset handling between Java `LocalDateTime` / `Instant` and SQL Server `DATETIME2(6)` / `DATETIMEOFFSET`.
4. Flyway Schema Migrations: DDL scripts `V003`, `V004`, `V005`, and `draft_m6` have not executed against an authentic SQL Server instance.

5.2 Minimum Prerequisites for Safe SQL Server E2E Execution:
To safely run SQL Server verification without risking data corruption or violating security policies:
1. Dedicated Database: Must target `HSWRMS_TEST` exclusively; connections to `HSWRMS`, `master`, or system databases are strictly prohibited.
2. Least-Privilege Credentials: Must use a dedicated test login (e.g. `[hswrms_test_user]`) with only `CONNECT` on `HSWRMS_TEST` for smoke testing, or dedicated application roles for integration tests. Administrative accounts (`sa`, `sysadmin`) are strictly forbidden.
3. Database Isolation: `HSWRMS_TEST` must have `READ_COMMITTED_SNAPSHOT` enabled (`ALTER DATABASE HSWRMS_TEST SET READ_COMMITTED_SNAPSHOT ON`).
4. Parameterized Provisioning: Execute provisioning strictly via the audited script `05_Development/database/scripts/provision_hswrms_test.ps1` with `-WhatIf` review before live execution.
5. Environment Variables: Credentials must be passed exclusively via environment variables:
   - `SQLSERVER_TEST_HOST=localhost`
   - `SQLSERVER_TEST_PORT=1433`
   - `SQLSERVER_TEST_DB=HSWRMS_TEST`
   - `SQLSERVER_TEST_USERNAME=hswrms_test_user`
   - `SQLSERVER_TEST_PASSWORD=<interactive-or-env-password>`
6. Explicit Opt-In: Smoke test execution requires `-Dhswrms.sqlserver.test.enabled=true`.

6. REFUND EXECUTION & KDS IMPLEMENTATION BOUNDARIES
================================================================================

6.1 Refund Execution Boundary:
- What is Implemented:
  * System Configuration: `refund_percentage` (default 80%, range 0–100%) and `cancellation_window_hours` (default 48h) exist in `SystemConfiguration` (M6) and are editable by delegated managers.
  * Payment Entity: `PaymentTransactionEntity.paymentStatus` supports enum value `'REFUNDED'`.
  * Booking Cancellation Status: `RetreatBookingService.cancelBooking` transitions booking status from `PENDING` or `CONFIRMED` to `CANCELLED`.
- What is Missing (Boundary):
  * Financial Calculation: No service computes refundable amount based on elapsed hours prior to arrival vs. `cancellation_window_hours`.
  * Payment Provider Integration: No VNPay Refund API client (`vnp_Command=refund`, `vnp_TransactionType=02/03`) exists.
  * Audit & Ledger: No financial credit note or refund payment transaction record is persisted upon cancellation.
  * Decision Required: Approval of refund business policy (full deposit forfeiture vs. prorated refund), manual receptionist refund approval vs. automated payment gateway refund, and VNPay merchant refund credentials.

6.2 Kitchen Display System (KDS) Boundary:
- What is Implemented:
  * Persistence: `MealOrderEntity` tracks booking, order date, meal period, order type (`DAILY_MEAL`, `A_LA_CARTE`), and status (`PENDING`, `PREPARING`, `READY`, `DELIVERED`, `CANCELLED`).
  * Repository & Billing Guard: `MealOrderRepository.findUnsettledOrdersForBooking` prevents premature invoice finalization and checkout. `findByIdWithLock` serializes charge posting and rejects daily meals (`CANNOT_CHARGE_INCLUDED_SERVICE`).
- What is Missing (Boundary):
  * REST API Endpoints: No controller exists to accept dining orders from guests or allow kitchen staff to transition order statuses (`PREPARING` -> `READY` -> `DELIVERED`).
  * Menu Catalog: No entity or database table exists for menu items, pricing, or nutritional/allergen attributes.
  * Real-Time Updates: Frontend KDS screens currently operate against a mock `DiningContext` with in-memory state.
  * Scoped Recommendation: If real-time KDS is required for Phase 6, a separate implementation phase should create `MealOrderService`, `MealOrderController`, menu item master data, and WebSocket or polling status updates.
