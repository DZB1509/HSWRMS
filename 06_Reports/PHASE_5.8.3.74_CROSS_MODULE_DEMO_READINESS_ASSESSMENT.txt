A. Booking Relationship & ID Flow (M2 <-> M3 <-> M4 <-> M5):
   - M2 Primary Key: `dbo.RetreatBooking.retreat_booking_id` (INT IDENTITY).
   - M3 Foreign Key: `dbo.SpaSession.retreat_booking_id` (INT, nullable for standalone walk-ins).
   - M4 Foreign Key: `dbo.MealOrder.retreat_booking_id` (INT NOT NULL).
   - M5 Foreign Key: `dbo.Folio.retreat_booking_id` (INT NOT NULL, UNIQUE).
   - Verification:
     * Frontend resolvers (`bookingResolver.ts`, `fnbIdUtils.ts`) strictly resolve positive integer IDs.
     * All backend entity associations use `Integer` / `Long` foreign keys mapping to `retreat_booking_id`.
     * Zero synthetic ID guessing; fail-closed behavior verified.

B. Persistence vs. Mock State Verification:
   - Backend contains zero in-memory collections; all controllers delegate to Spring Data JPA repositories.
   - Frontend contexts (`CustomerContext`, `SpaContext`, `DiningContext`, `FolioContext`, `GovernanceContext`)
     support hybrid operation: when backend is online and booking ID is present, they communicate directly with
     real REST endpoints. When backend calls fail, `DiningContext` and `FolioContext` roll back optimistic state
     and present visible error banners, eliminating false-success illusions.

C. Financial Idempotency & Server-Authoritative Pricing:
   - M4 Dining: Client sends only `{ menuItemId, quantity }`. Backend calculates line items and total from `dbo.MenuItem.price`.
   - M5 Billing: `FolioBillingService.postFolioCharge` uses `source_type` and `source_reference_id` to prevent duplicate billing charges.
   - Folio finalization locks the invoice: once generated, line items cannot be mutated.

[P1-01] ROLE AUTHORITY MISMATCH FOR DEDICATED F&B STAFF PERSONA
- Severity: P1 (High — Demo Workflow Blocker for F&B Staff Persona)
- Affected Module: M1 (Identity/Bootstrap) & M4 (Kitchen Display System Authorization)
- Specific Locations:
  * `05_Development/backend/src/main/java/com/heavenstay/hswrms/config/DevAccountBootstrap.java` (line 66)
  * `05_Development/backend/src/main/java/com/heavenstay/hswrms/config/SecurityConfig.java` (line 153)
  * `05_Development/backend/src/main/java/com/heavenstay/hswrms/security/CustomUserDetails.java` (line 27)
  * `05_Development/backend/src/main/java/com/heavenstay/hswrms/m4fnb/controller/FnbKdsController.java` (lines 39, 51, 67, 77, 92)
- Direct Evidence:
  * `DevAccountBootstrap` seeds the role with name `"F&B Staff"`.
  * When `fbstaff@heavenstay.dev` logs in, `AuthService.login()` reads `Role.getRoleName()` = `"F&B Staff"`.
  * `CustomUserDetails` transforms this into authority `"ROLE_F&B STAFF"`.
  * `SecurityConfig` and `FnbKdsController` check `hasAnyRole("FNB_STAFF", "MANAGER", "ADMIN")`, which requires authority `"ROLE_FNB_STAFF"`.
  * String comparison fails: `"ROLE_F&B STAFF"` != `"ROLE_FNB_STAFF"`.
- Status: Confirmed by static code review.
- Impact on Demo:
  * When demonstrating as `fbstaff@heavenstay.dev`, accessing `/api/v1/fnb/kds/**` yields **HTTP 403 Forbidden**.
  * Workaround for demo: Managers (`manager@heavenstay.dev`) and Admins (`admin@heavenstay.dev`) CAN access KDS because their roles match `ROLE_MANAGER` and `ROLE_ADMIN`. However, the dedicated chef/kitchen staff persona fails.
- Minimal Remediation:
  * Normalize role authority in `CustomUserDetails.java`: if role is `"F&B Staff"`, map to `"ROLE_FNB_STAFF"`. Alternatively, add `"F&B STAFF"` to `SecurityConfig` and `FnbKdsController` role checks.

[P1-02] DATABASE SCHEMA NOT AUTOMATICALLY CREATED IN DEV/PROD
- Severity: P1 (High — Deployment & Live Demo Prerequisite)
- Affected Module: Infrastructure / Database
- Specific Locations:
  * `05_Development/backend/src/main/resources/application.yml` (line 29: `ddl-auto: none`)
- Direct Evidence:
  * The backend has no Flyway/Liquibase dependency in `pom.xml`.
  * In non-test profiles (`dev` and `prod`), `ddl-auto: none` prevents Hibernate from creating or modifying tables.
  * If Spring Boot starts against a fresh SQL Server database without running `schema.sql` first, startup crashes with table missing errors.
- Status: Confirmed by configuration review.
- Impact on Demo:
  * Live demo requires manual execution of `05_Development/database/schema.sql` on SQL Server prior to backend startup.
- Minimal Remediation:
  * Run `schema.sql` via `sqlcmd` on the target database, and set `SEED_DEMO_DATA=true` to populate initial stay data.

[P2-01] VNPAY SANDBOX CREDENTIAL DEPENDENCY IN CHECKOUT
- Severity: P2 (Medium — Flow Dependency)
- Affected Module: M2 (Deposit) & M5 (Final Payment)
- Specific Locations:
  * `05_Development/backend/src/main/resources/application.yml` (lines 83-87)
  * `05_Development/backend/src/main/java/com/heavenstay/hswrms/m2booking/service/VNPayDepositService.java`
- Direct Evidence:
  * If `VNPAY_HASH_SECRET` is blank and `app.vnpay.mock-auto-confirm=false`, VNPay URL generation fails.

- Minimal Remediation:
  * Ensure `VNPAY_MOCK_AUTO_CONFIRM=true` is set in the demo environment variables so VNPay payments auto-confirm seamlessly.

[P3-01] CROSS-ORIGIN RESOURCE SHARING (CORS) IN HOSTED TOPOLOGIES
