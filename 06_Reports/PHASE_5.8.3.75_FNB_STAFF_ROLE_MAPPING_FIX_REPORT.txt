1. ROOT CAUSE VERIFICATION & ANALYSIS
--------------------------------------------------------------------------------
1.1 Discrepancy Between Database Role Name & Spring Security Convention
    - Authoritative database schema (`05_Development/database/schema.sql` line 161)
      and bootstrap seed (`DevAccountBootstrap.java` line 66 & 75) declare the canonical
      role name as:
        Role ID 4: N'F&B Staff'
        Account: fbstaff@heavenstay.dev -> Role: 'F&B Staff'
    - Spring Security configuration (`SecurityConfig.java` line 153),
      controller annotations (`FnbKdsController.java` lines 39, 51, 67, 77, 92),
      and role constants (`Role.FNB_STAFF = "FNB_STAFF"`) check:
        hasAnyRole('FNB_STAFF', 'MANAGER', 'ADMIN')
        which requires GrantedAuthority: "ROLE_FNB_STAFF"
    - In `FnbCustomerOrderController.java` (line 83), staff authorization checks:
        .anyMatch(a -> a.getAuthority().equals("ROLE_FNB_STAFF"))

1.2 Failure Mechanism in Runtime
    - When `fbstaff@heavenstay.dev` logs in, `AuthService.login()` reads the role
      name from DB entity `Role.getRoleName()` -> "F&B Staff".
    - `AuthService` issues a JWT containing claims `roles = ["F&B Staff"]`.
    - On every API call, `JwtAuthenticationFilter` resolves claims and calls:
        new CustomUserDetails(userId, email, "", fullName, true, roles);
    - In previous code of `CustomUserDetails.java` (lines 26-30):
        this.authorities = roles.stream()
            .map(role -> role.startsWith("ROLE_") ? role : "ROLE_" + role.toUpperCase())
            .map(SimpleGrantedAuthority::new)
            .collect(Collectors.toList());
    - Evaluating "F&B Staff":
        "ROLE_" + "F&B Staff".toUpperCase() => "ROLE_F&B STAFF"
    - Spring Security's `hasRole("FNB_STAFF")` and `hasAnyRole("FNB_STAFF", ...)`
      looks strictly for "ROLE_FNB_STAFF".
    - Because "ROLE_F&B STAFF" != "ROLE_FNB_STAFF", Spring Security immediately
      rejected the user with HTTP 403 Forbidden!

1.3 Masking in Previous Tests
    - `FnbControllersSecurityTest.java` (line 116) previously bypassed this bug by
      manually passing `List.of("FNB_STAFF")` to `jwtTokenProvider.generateToken()`,
      never exercising the actual database role string "F&B Staff" returned by `AuthService`.
