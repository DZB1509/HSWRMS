     via migrations V006 and V007. Running Workspace B code on the baseline
     database will crash immediately with JPA `SQLException: Invalid column name`.
3. P1 Architectural & Functional Mismatches in Workspace B:
   - Missing Order Cancellation & Terminal State Violation: Workspace B provides
     no cancellation endpoints or service methods. Its state machine transition
     validator even allows DELIVERED -> CANCELLED, violating terminal state rules.

     FEFO ingredient batch deduction, directly violating the explicit project rule

     delegation, and rejecting ADMIN and MANAGER with 403 on kitchen operations.
4. Cancellation Reason Persistence Gap:
   - In Workspace A, cancellation reason is validated at runtime and logged to
     application logs via SLF4J, but is NOT persisted to `dbo.AuditLog` or `dbo.MealOrder`
     due to lack of schema columns. Workspace B has no cancellation implementation.
5. Strategic Recommendation:
   - RETAIN WORKSPACE A as the authoritative operational baseline (KEEP_A).
   - DO NOT perform any automated directory overwrite or blanket merge.
   - Selectively adopt valuable conceptual assets from Workspace B in subsequent

4. BUSINESS-RULE AND STATE MACHINE COMPARISON
================================================================================

Rule 1: Customer cancellation allowed only in PENDING.
- Workspace A: Enforced. `cancelOrderInternal` checks `if ("PENDING".equals(currentStatus))` and
  validates customer ownership via `validateBookingOwnership`. If customer attempts to cancel
  when order is PREPARING, it throws `CUSTOMER_CANNOT_CANCEL_PREPARING_ORDER`.
- Workspace B: VIOLATED / ABSENT. Workspace B has no cancellation endpoint or service method.
  Customers cannot cancel their orders at all.

Rule 2: Authorized staff may cancel from PREPARING onward and must provide a reason.
- Workspace A: Enforced. If order is PREPARING or READY, staff cancellation is permitted but
  explicitly validates `if (cancellationReason == null || cancellationReason.trim().isEmpty())`
  and throws `CANCELLATION_REASON_REQUIRED`.
- Workspace B: ABSENT. No cancellation method exists.

Rule 3: A-la-carte charges posted to M5 Folio when order transitions to DELIVERED.
- Workspace A: Enforced. `postFolioChargeIfEligible` is invoked inside `updateOrderStatus`
  strictly when `targetStatus` is `DELIVERED`.
- Workspace B: CRITICALLY VIOLATED (P0-1). `MealOrderServiceImpl.placeAlaCarteOrder` publishes
  `AlaCarteOrderPlacedEvent`, causing `M4FolioChargeEventListener` to post Folio charges
  immediately when the order is created in PENDING state!

Rule 4: Cancelled orders are not charged.
- Workspace A: Enforced. Since charges are posted only at DELIVERED, cancelled orders never incur charges.
- Workspace B: VIOLATED. Because orders are charged at PENDING, any rejected/cancelled order has
  already been charged to the customer's Folio.

Rule 5: Idempotency & duplicate Folio charge prevention.
- Workspace A: Enforced. `folioItemRepository.existsBySourceMealOrderId(orderId)` prevents duplicate
  postings on retries or repeated status transitions. Furthermore, if `postFolioCharge` fails,
  the transaction rolls back atomically.
- Workspace B: Weak / Broken. Event listener catches `Exception` and logs a warning with `log.warn`,
  swallowing the failure. If Folio posting fails, order creation still succeeds without charge,
  causing silent unbilled food consumption.

Rule 6: Server-calculated prices are authoritative.
- Workspace A: Enforced. `postFolioChargeIfEligible` calculates totals from server-side `MenuItem.price`.
  Client-submitted totals are ignored.
- Workspace B: Enforced on backend (`orderItem.setUnitPrice(menuItem.getPrice())`).

Rule 7: Inventory uses availability_status; no ingredient-batch deduction.
- Workspace A: Enforced. Conforms strictly to baseline `availability_status` on `MenuItemEntity`.
- Workspace B: VIOLATED. Workspace B implemented full ingredient inventory deduction in
  `InventoryServiceImpl.processConsumptionForOrderItem`, deducting stock from batches using FEFO.

Rule 8: Terminal state immutability.
- Workspace A: Enforced. DELIVERED orders cannot be cancelled (`ORDER_ALREADY_DELIVERED`).
- Workspace B: VIOLATED. Line 380 of `MealOrderServiceImpl.java` allows `DELIVERED -> CANCELLED`
  in `isAllowedTransition`:
  `case DELIVERED -> target == MealOrderStatus.CANCELLED;`

6. CANCELLATION REASON PERSISTENCE ASSESSMENT
================================================================================

Verification against both workspaces and SQL schema:
1. Schema verification:
   Neither the baseline `dbo.MealOrder` table nor Workspace B's migration `V006`
   contains a `cancellation_reason` column.
2. Workspace A behavior:
   In `MealOrderServiceImpl.java`, `cancellationReason` is rigorously validated:
   - For staff cancellations from PREPARING or READY, a non-empty reason is mandatory
     (`CANCELLATION_REASON_REQUIRED`).
   - The reason is logged using SLF4J:
     `log.warn("Order ID {} in {} state cancelled by staff {}. Reason: {}", orderId, status, userId, cancellationReason);`
   - DISCOVERY: The reason is NOT currently written to `dbo.AuditLog` via `AuditLogService`.
     Therefore, the cancellation reason is not durable in the database and cannot be
     retrieved via SQL query or REST API after application restarts.
3. Workspace B behavior:
   Workspace B has no cancellation implementation whatsoever. No cancellation reason
   is validated, logged, or persisted.
4. Recommendation for Next Phase:
   In the upcoming integration phase, enhance `MealOrderServiceImpl.cancelOrderInternal`
   in Workspace A by injecting `AuditLogService` and recording an audit record:
   `auditLogService.logAction("CANCEL_MEAL_ORDER", "MealOrder", orderId, currentUserId, "Reason: " + cancellationReason);`
   This achieves durable, retrievable persistence without requiring database DDL changes.
