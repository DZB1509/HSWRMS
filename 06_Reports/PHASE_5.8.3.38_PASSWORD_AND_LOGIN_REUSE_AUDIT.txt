B. Lexical Mechanics of SQLCMD Macro Substitution:
  - SQLCMD variable substitution is pure textual replacement prior to T-SQL parsing.
  - In T-SQL DDL, 'CREATE LOGIN ... WITH PASSWORD = N''...''' requires a string literal.
    SQL Server does NOT support parameterized DDL (e.g. WITH PASSWORD = @pwd is invalid).
  - Consequently, the substituted text must adhere to strict lexical constraints so
    it does not break the single-quote literal delimiters in T-SQL or double-quote
    delimiters in ':setvar'.

C. Empirical Results Across 10 Synthetic Test Cases:
  An isolated, non-mutating test harness evaluated representative synthetic inputs
  against SQLCMD and SQL Server's query compiler:

  SYNTH_04_BLOCK_COMMENT Synthetic/*Pass*/123!                    0      True      False

D. Key Quoting Behaviors & Safety Guarantees:
  1. Semicolons, Comment Markers, Parentheses:
     Within single quotes (e.g. N'Synthetic;--Pass/*comment*/)123!'), semicolons do NOT
     terminate statements, comment markers do NOT truncate code, and parentheses do NOT
     alter T-SQL block structure. SQL Server compiles them as literal characters.
  2. Single Quote Collision:
     An unescaped single quote (') terminates the literal string N'$(TEST_PASSWORD)'
     prematurely. In SYNTH_08 and SYNTH_09, this immediately triggered Msg 4145 (Level 15).
     Because ':on error exit' is active, SQLCMD halted immediately (ExitCode 1).
     Zero mutations occurred; injected statements were NEVER executed.
  3. Secret Echo Mitigation:
     Because SQL Server Msg 4145/Msg 105 can print "near '...'", single quotes risk
     echoing trailing fragments of the input to the console. Therefore, single quotes
     are strictly prohibited.
  4. Script Error Outputs:
     Stage 0 and Stage 3 guards in 'draft_provision_hswrms_test.sql' emit static,
     hardcoded error strings:
     "RAISERROR('FAIL CLOSED: Test password is missing, unresolved, or set to a placeholder.', 16, 1);"
     The script NEVER formats $(TEST_PASSWORD) into error messages or log output.

E. Formal Accepted Password Policy (Documented in Section 2.D of Guide):
  - Length: Minimum 12 characters.
  - Categories: Minimum 3 of (uppercase, lowercase, digits, allowed symbols).
  - Allowed Characters: A-Z, a-z, 0-9, and symbols:
    ! @ # $ % ^ & * ( ) - _ = + [ ] { } | : ; , . < > ? / ~
  - Strictly Prohibited Characters:
    * Single Quote (') — prevents T-SQL literal boundary breakage and syntax error echoes.
    * Double Quote (") — prevents SQLCMD :setvar command syntax collisions.
    * Macro Sequence ($() — prevents recursive or unexpanded SQLCMD macro errors.

4. TASK 2: EXISTING LOGIN BEHAVIOR & CRYPTOGRAPHIC REALITY AUDIT
================================================================================
A. Behavioral Trace Under Different Login States:
  1. When [hswrms_test_user] Does NOT Exist:
     - Stage 1.3 evaluates FALSE; pre-check passes cleanly.
     - Stage 3 evaluates TRUE; executes CREATE LOGIN with $(TEST_PASSWORD).
     - Result: Clean, synchronized login creation.
  2. When [hswrms_test_user] Exists and ALLOW_EXISTING_LOGIN is 'FALSE' (Default):
     - Stage 1.3 evaluates TRUE; triggers RAISERROR (severity 16), SET NOEXEC ON, RETURN.
     - ':on error exit' terminates CLI sqlcmd immediately with exit code 1.
     - Result: Fail closed by default. Zero mutations occur.
  3. When [hswrms_test_user] Exists and ALLOW_EXISTING_LOGIN is 'TRUE':
     - Stage 1.3 validates login type (must be SQL login 'S'), is_disabled (must be 0),
       default_database_name (must be 'HSWRMS_TEST' or 'master', never 'HSWRMS'),
       0 server roles, and 0 server permissions.
     - If all pass, Stage 3 skips CREATE LOGIN (IF NOT EXISTS is false).
     - Stage 3 prints: "[INFO] Login [hswrms_test_user] already exists. Skipping creation."

B. Password Matching Invariant & Cryptographic Reality:
  - Can the script guarantee that $(TEST_PASSWORD) matches the existing login password?
    NO. ABSOLUTELY NOT.
  - Technical Justification:
    * SQL Server stores password hashes in 'sys.sql_logins.password_hash' using salted
      SHA-512 (Password Hash Version 2).
    * Password hashes are non-reversible (one-way cryptographic hash).
    * SQL Server exposes NO system function or DMV to verify whether an arbitrary
      plaintext password matches a login's stored hash.
    * Therefore, no script or query can infer or confirm password parity from metadata.
  - Operational Consequence:
    If an existing login is reused and $(TEST_PASSWORD) differs from the existing
    password, Stage A will report success, but Stage B (Live JDBC Smoke Test) will
    fail with SQL Server Error 18456 (Login failed for user 'hswrms_test_user').

C. Independent Verification Requirements for Login Reuse:
  Initial Stage A provisioning is designed and recommended for a CLEAN SLATE where
  [hswrms_test_user] does NOT exist.
  If reuse is ever approved:
    1. The operator must verify that the password stored in their environment matches
       the existing login, OR
    2. The operator must administratively synchronize the password in a dedicated
       SSMS administrative session prior to Stage B:
       ALTER LOGIN [hswrms_test_user] WITH PASSWORD = N'...';

6. UNRESOLVED LIMITATIONS & RISK DISCLOSURES
================================================================================
1. Direct Text Substitution:
   SQLCMD performs lexical replacement without DDL parameterization. Password safety
   relies on adhering to the accepted character set (avoiding single and double quotes).
2. Local Credential Persistence Constraints:
   Neither SSMS unsaved buffers nor process environment variables provide an absolute
   guarantee of zero disk footprint. SSMS AutoRecover snapshots, OS virtual memory
   paging (pagefile.sys), and clipboard history remain system-level considerations.
3. Existing Login Password Parity:
   Because SQL Server passwords cannot be verified against stored hashes, clean
   initial provisioning (login absent before Stage A) is the only mode that guarantees
   credential synchronization.
