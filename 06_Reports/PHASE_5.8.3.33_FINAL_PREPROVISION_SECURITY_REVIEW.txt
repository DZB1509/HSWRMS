5. FINDINGS: SQLCMD PASSWORD GUARD BEHAVIOR
--------------------------------------------------------------------------------
Static Inspection & Control-Flow Analysis of `draft_provision_hswrms_test.sql`:

A. Is SQLCMD Mode Required?
   - YES.
   - Mechanism: Line 31 contains `:on error exit` and lines 37-38 contain `:setvar` commands.
   - In SSMS standard mode (non-SQLCMD), executing a script containing `:` commands immediately
     causes SSMS to throw a syntax error.
   - In addition, Batch 2 defines `:setvar SQLCMD_MODE_CHECK "SQLCMD_ACTIVE"`. Batch 3 checks:
     `IF '$(SQLCMD_MODE_CHECK)' <> 'SQLCMD_ACTIVE' BEGIN RAISERROR(...); SET NOEXEC ON; END`.
     If SQLCMD mode is inactive, `$(SQLCMD_MODE_CHECK)` is not replaced by the preprocessor,
     causing the conditional check to evaluate to TRUE, raising an explicit error and executing
     `SET NOEXEC ON`.

B. Detection of Undefined TEST_PASSWORD:
   - When executed via `sqlcmd.exe` without `-v TEST_PASSWORD="..."`, line 37 defines the fallback
     value: `:setvar TEST_PASSWORD "REPLACE_WITH_STRONG_PASSWORD_BEFORE_EXECUTION"`.
   - Batch 4 checks whether `$(TEST_PASSWORD)` equals empty string or either known placeholder
     (`REPLACE_WITH_STRONG_PASSWORD_BEFORE_EXECUTION` or `CHANGE_ME_STRONG_PASSWORD!`).
   - If undefined or set to placeholder, the guard raises an error and halts execution.

C. Rejection of Placeholder or Empty Password:
   - Batch 4 explicitly evaluates:
     `IF '$(TEST_PASSWORD)' = '' OR '$(TEST_PASSWORD)' = 'REPLACE_WITH_STRONG_PASSWORD_BEFORE_EXECUTION' OR '$(TEST_PASSWORD)' = 'CHANGE_ME_STRONG_PASSWORD!'`
   - When triggered, it raises severity 16 error:
     "FAIL CLOSED: A strong password must be supplied via $(TEST_PASSWORD). Default placeholders are forbidden."
     and executes `SET NOEXEC ON;`.

D. Impact of `SET NOEXEC ON` on Session State:
   - In Microsoft SQL Server, `SET NOEXEC ON` causes the database engine to parse and compile
     subsequent batches in the session, but NOT execute them.
   - We verified empirically on the local SQL Server 2019 Express instance: `SET NOEXEC ON`
     persists across all subsequent `GO` batches within the same connection until either
     `SET NOEXEC OFF` is executed or the connection is terminated.
   - When run via `sqlcmd.exe`, `:on error exit` ensures that the CLI process exits immediately
     with a non-zero exit code upon encountering the `RAISERROR`.
   - When run interactively in SSMS, `SET NOEXEC ON` prevents any mutations in subsequent batches.
     The operator must execute `SET NOEXEC OFF;` or close the SSMS query window to reset session state.
     A prominent warning is documented in the script header and provisioning guide.

E. Pre-Guard Statement Analysis:
   - Lines 1-30: Comments and documentation only.
   - Line 31: `:on error exit` (SQLCMD directive).
   - Lines 37-38: Variable declarations (`:setvar`).
   - Lines 41-45: SQLCMD mode validation.
   - Lines 48-54: Password safety validation.
   - Finding: ZERO DDL, DML, or state-changing statements execute before the guards.
     The first statement that touches SQL Server state is `USE [master];` in Batch 5.

F. Can the Script Continue After a Failed Precondition?
   - NO.
   - Under `sqlcmd.exe`: `:on error exit` terminates process execution on severity 16 errors.
   - Under SSMS: `SET NOEXEC ON` suppresses execution of all subsequent batches in the session.

G. Can a Failure Leave a Partially Provisioned Environment?
   - In normal execution, if a later stage fails (e.g. Stage 2 succeeds in creating HSWRMS_TEST,
     but Stage 3 fails due to Windows password complexity policy), the database exists but the
     login is not created.
   - Risk Assessment: Zero risk to production/development data. [HSWRMS_TEST] is an isolated,
     empty database that contains no application data and cannot affect [HSWRMS].
   - Idempotency & Recovery: Every stage uses `IF NOT EXISTS` guards and validates object health.
     If re-run after correcting password policy, Stage 2 detects existing ONLINE database and
     skips creation, proceeding directly to Stage 3. Stage-by-stage recovery procedures are
     documented in Section 5 of `HSWRMS_TEST_PROVISIONING_GUIDE.md`.

8. FINDINGS: DATABASE CONNECT-ONLY PERMISSIONS
--------------------------------------------------------------------------------
A. Principle of Least Privilege:
   - In earlier preliminary drafts, `db_datareader` was proposed.
   - In Phase 5.8.3.32 and 5.8.3.33, this was eliminated because `db_datareader` grants
     database-wide `SELECT` access across all user tables.
   - The proposed principal receives strictly:
     `GRANT CONNECT TO [hswrms_test_user];` in [HSWRMS_TEST].
   - ZERO membership in `db_datareader`, `db_datawriter`, `db_owner`, or custom data roles.
   - Stage 4 of `draft_provision_hswrms_test.sql` validates that `hswrms_test_user` in [HSWRMS_TEST]
     belongs to no database roles other than `public`.

B. What `CONNECT` Allows vs What It Does Not Allow:
   - What `CONNECT` Allows:
     * Establishes a session with database [HSWRMS_TEST].
     * Executes queries permitted to database role `public`.
     * In SQL Server, `public` can execute built-in scalar functions: `@@VERSION`, `DB_NAME()`,
       `SCHEMA_NAME()`, `USER_NAME()`, `SUSER_SNAME()`.
     * Queries standard database metadata visible to all database users.
   - What `CONNECT` Does NOT Allow:
     * Cannot read from user tables or views (requires SELECT).
     * Cannot insert, update, or delete rows in user tables (requires INSERT, UPDATE, DELETE).
     * Cannot create, alter, or drop tables, schemas, or procedures (requires DDL permissions).
     * Cannot execute stored procedures unless explicitly granted or granted to public.
     * Cannot access other databases where user mapping or guest is disabled.

C. Smoke Test Query Compatibility:
   - Query in `SqlServerJdbcSmokeTest.java:104`:
     `SELECT @@VERSION AS [version], DB_NAME() AS [db_name]`
   - Both `@@VERSION` and `DB_NAME()` are scalar system functions.
   - They execute successfully under `public` without requiring user table access.
   - Connection is marked `connection.setReadOnly(true)`.
   - Conclusion: `CONNECT` permission is 100% sufficient to satisfy the JDBC smoke test.
     Zero permissions need to be broadened.
