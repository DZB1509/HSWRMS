3. DETAILED BREAKDOWN OF CREDENTIAL-SAFETY CORRECTIONS
--------------------------------------------------------------------------------
A. Elimination of Persistent Password in Source Script:
   - Previous Weakness: [draft_provision_hswrms_test.sql] contained
     ':setvar TEST_PASSWORD "REPLACE_WITH_STRONG_PASSWORD_BEFORE_EXECUTION"'.
     In SQLCMD, an in-script :setvar overrides any variable passed from the environment,
     forcing operators to edit the script file and risk saving plaintext passwords to disk.
   - Correction: Removed :setvar TEST_PASSWORD from the script. Added explicit comments
     warning that passwords must NEVER be saved to the file. The script now expects
     $(TEST_PASSWORD) to be supplied transiently at runtime.

B. Elimination of Command-Line Argument Passing:
   - Previous Weakness: [HSWRMS_TEST_PROVISIONING_GUIDE.md] previously suggested
     'sqlcmd -S localhost -E -v TEST_PASSWORD="..."'.
   - Security Exposure: Process command lines in Windows are queryable by any user
     or process on the local machine via 'Get-CimInstance Win32_Process', Task Manager,
     or sysinternals Process Explorer, and are logged to Windows Event ID 4688 if
     process auditing is enabled.
   - Correction: Removed all '-v TEST_PASSWORD="..."' examples from the guide.

C. Correction of SecureString Misconception:
   - Previous Weakness: Informal notes mentioned 'Read-Host -AsSecureString' as if
     the resulting object could be passed directly into SQLCMD.
   - Technical Reality: 'Read-Host -AsSecureString' yields a System.Security.SecureString.
     Passing it as a string argument to native executables results in the literal
     string "System.Security.SecureString", causing login creation to use that literal
     type name as the password.
   - Correction: The guide now explains the exact Marshal SecureStringToBSTR / PtrToStringBSTR
     pattern to transiently unprotect the string in memory when using the CLI method,
     and immediately zeroes and frees the BSTR pointer and variables afterward.

D. Recommended Practical Execution Approaches:
   - Method 1: Interactive SSMS in an Unsaved Query Tab (Primary Recommended):
     1. Open SSMS and connect via Windows Authentication (-E).
     2. Press Ctrl+N to open a New Query tab (unsaved editor buffer).
     3. Select Query menu -> SQLCMD Mode.
     4. On line 1, enter: :setvar TEST_PASSWORD "<StrongPassword>".
     5. Copy and paste the contents of [draft_provision_hswrms_test.sql] below line 1.
     6. Execute (F5).
     7. Close the tab without saving (click "Don't Save").
     Audit Assessment: Zero disk persistence, zero command-line argument leakage,
     zero shell history recording, zero persistent environment variables.
   - Method 2: Ephemeral Process-Scoped PowerShell Execution (CLI Alternative):
     Captures password via Read-Host -AsSecureString, transiently assigns to $env:TEST_PASSWORD,
     runs 'sqlcmd -S localhost -E -i ...' without -v (sqlcmd automatically inherits
     process environment variables as scripting variables), and immediately nulls $env:TEST_PASSWORD.

E. SQLCMD Variable Substitution & Robust Error Termination:
   - Missing Variable Behavior: Verified empirically on local SQL Server 2019 Express:
     When TEST_PASSWORD is undefined, ':on error exit' at line 1 immediately halts
     the SQLCMD preprocessor with error: "'TEST_PASSWORD' scripting variable not defined."
     and terminates the process with exit code 1. Zero SQL batches execute.
   - Unresolved Placeholder Detection: If SQLCMD substitution fails and passes literal
     text, Stage 0 checks 'LEFT('$(TEST_PASSWORD)', 2) = '$' + '('' and halts.
   - Beyond SET NOEXEC ON: To ensure failure does not rely solely on SET NOEXEC ON,
     every failure block now pairs RAISERROR, SET NOEXEC ON, and RETURN.
   - Inline Stage 3 DDL Guard: Added an explicit inline guard immediately before
     'CREATE LOGIN' in Stage 3 to re-validate $(TEST_PASSWORD) before mutating state.
