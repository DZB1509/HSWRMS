2. ROOT-CAUSE DIAGNOSIS & REMEDIATION OF HARNESS STALL
================================================================================
Background:
  During the initial execution of scratch/test_safer_provisioning_harness.ps1,
  PowerShell child processes (PIDs 5840 and 4696) appeared stalled for nearly 20
  minutes with 0% CPU consumption over a 60-second measurement window.

Process & Task Inspection:
  - Task state in IDE: Background task task-7686 was holding the child process.
  - Process tree: powershell.exe (PID 5840) spawned by the tool runner, hosting
    the test harness script, which in turn spawned child powershell.exe (PID 4696).
  - CPU usage: 0.00% CPU activity across 60 seconds.
  - State: Blocked waiting on synchronous console stdin read.
  - Protected process check: Language server PID 12140 was inspected and verified
    completely unrelated; PID 12140 was NOT touched or signaled.

Root Cause Analysis:
  In the initial implementation of provision_hswrms_test.ps1, credential handling
  was structured as:
    if (-not [string]::IsNullOrEmpty($PlaintextPasswordForTesting)) {
        $plainPass = $PlaintextPasswordForTesting
    }
    elseif ($TestPassword -ne $null) {
        ...
    }
    else {
        $sec = Read-Host -Prompt "Enter HSWRMS test password (min 12 chars)" -AsSecureString
        ...
    }

  When test case VAL_01_EMPTY executed:
    & $scriptPath -DryRun -PlaintextPasswordForTesting ""
  The parameter $PlaintextPasswordForTesting was explicitly passed, but its value
  was [string]::Empty ("").
  Consequently, [string]::IsNullOrEmpty("") evaluated to $true.
  Therefore, '-not [string]::IsNullOrEmpty("")' evaluated to $false!
  The script failed the first 'if', skipped the 'elseif', and entered the 'else'
  block, invoking:
    Read-Host -Prompt "Enter HSWRMS test password (min 12 chars)" -AsSecureString

  Because the script was executing inside an automated background PowerShell process
  with standard input redirected and no interactive operator attached, Read-Host
  blocked indefinitely awaiting console keystrokes, completely halting the pipeline.

Cancellation & Remediation:
  1. Safe Task Termination: The stalled task task-7686 was cancelled via the IDE's
     manage_task 'kill' action. Child PIDs 5840 and 4696 were terminated cleanly.
     Antigravity language server PID 12140 remained running and undisturbed.
  2. Bound Parameter Detection Fix: Replaced IsNullOrEmpty checks with PowerShell's
     built-in $PSBoundParameters dictionary:
       if ($PSBoundParameters.ContainsKey('PlaintextPasswordForTesting')) {
           $plainPass = $PlaintextPasswordForTesting
       }
       elseif ($PSBoundParameters.ContainsKey('TestPassword')) {
           if ($TestPassword -ne $null) {
               $bstr = [System.Runtime.InteropServices.Marshal]::SecureStringToBSTR($TestPassword)
               $plainPass = [System.Runtime.InteropServices.Marshal]::PtrToStringBSTR($bstr)
           } else {
               $plainPass = $null
           }
       }
       else {
           $sec = Read-Host -Prompt "Enter HSWRMS test password (min 12 chars)" -AsSecureString
           ...
       }
  3. Result: When -PlaintextPasswordForTesting "" is passed, $PSBoundParameters.ContainsKey
     evaluates to $true, assigning "" directly to $plainPass. Execution proceeds
     immediately to Test-HswrmsProvisioningInput, which evaluates:
       if ([string]::IsNullOrEmpty($Password)) {
           throw "VALIDATION ERROR: Password is required and cannot be null or empty."
       }
     This throws an immediate terminating exception without prompting Read-Host,
     allowing the test harness to catch the error, mark VAL_01_EMPTY as REJECTED
     [PASS], and complete instantaneously.

B. -WhatIf and -DryRun Guarding Analysis:
   In PowerShell, declaring '[CmdletBinding(SupportsShouldProcess = $true)]' registers
   the -WhatIf and -Confirm parameters on the cmdlet or script. However, native .NET
   API calls (such as $conn.Open() or $cmd.ExecuteNonQuery()) are NOT automatically
   intercepted by PowerShell engine hooks. Relying on SupportsShouldProcess alone
   without checking $PSCmdlet.ShouldProcess() would allow .NET DDL commands to execute
   even when -WhatIf is specified.

   Audit of provision_hswrms_test.ps1 confirms robust, multi-layer guarding:
   1. Pre-Connection Guard (Line 180):
      $isWhatIf = ($DryRun -or (-not $PSCmdlet.ShouldProcess("SQL Server instance '$ServerInstance'", "Execute Stage A Provisioning (Database [$DatabaseName], Login [$LoginName])")))
      if ($isWhatIf) {
          Write-Host "[DRY RUN PASS] All client-side validations passed successfully."
          ...
          return
      }
      Behavior: When -WhatIf is passed, $PSCmdlet.ShouldProcess emits the standard
      PowerShell What-If notification:
        "What if: Performing the operation "Execute Stage A Provisioning..." on target "SQL Server instance 'localhost'"."
      It returns $false, causing $isWhatIf to evaluate to $true, and the script
      exits at Line 195. ZERO database connections are opened, zero TCP sockets are
      connected, and zero SQL queries are sent.
   2. Defense-in-Depth DDL Operation Guards:
      Even if the pre-connection guard were removed, each individual DDL mutation is
      explicitly guarded by its own $PSCmdlet.ShouldProcess() invocation:
        - Stage 2 (Line 314):
          if ($PSCmdlet.ShouldProcess("SQL Server instance '$ServerInstance'", "CREATE DATABASE [$DatabaseName]")) {
              $null = $cmd.ExecuteNonQuery()
          }
        - Stage 3 (Line 336):
          if ($PSCmdlet.ShouldProcess("SQL Server instance '$ServerInstance'", "CREATE LOGIN [$LoginName]")) {
              $null = $cmd.ExecuteNonQuery()
          }
        - Stage 4 (Line 359):
          if ($PSCmdlet.ShouldProcess("Database [$DatabaseName]", "CREATE USER [$LoginName] and GRANT CONNECT")) {
              $null = $cmd.ExecuteNonQuery()
          }
