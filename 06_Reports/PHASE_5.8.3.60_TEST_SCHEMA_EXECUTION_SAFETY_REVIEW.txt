3. TARGET GUARD BEHAVIOR & EXECUTION SEMANTICS ANALYSIS
--------------------------------------------------------------------------------
A. Analysis of the Guard Components:
   1. `USE [HSWRMS_TEST]; GO` (Batch 1):
      - Switches the active database catalog to `HSWRMS_TEST`.
      - If `HSWRMS_TEST` does not exist or connecting user lacks access, SQL Server
        issues Error 911 (Severity 16).
      - Under `sqlcmd -b`, Error 911 causes immediate process exit (ERRORLEVEL 1).
      - If `-b` is omitted, SQLCMD prints the error and proceeds to Batch 2.

   2. `IF DB_NAME() <> N'HSWRMS_TEST'` (Batch 2):
      - Evaluates the current active catalog returned by SQL Server engine function `DB_NAME()`.
      - If context switch succeeded, condition is FALSE; guard does not fire.
      - If context switch failed (or script was piped into another database without switching),
        condition is TRUE; execution enters the fail-closed block.

   3. `SET NOEXEC ON;` (Batch 2):
      - Instructs the SQL Server query processor to parse and compile syntax but
        REFUSE TO EXECUTE any statements.
      - Crucial T-SQL Semantic: In SQL Server, `SET NOEXEC ON` is connection/session-scoped.
        It persists across `GO` batch boundaries within the same connection until
        explicitly disabled with `SET NOEXEC OFF` or until disconnection.
      - Because `SET NOEXEC ON` is placed BEFORE `THROW 51000`, the flag is armed
        before the error is raised.

   4. `THROW 51000, N'...', 1;` (Batch 2):
      - Raises a user-defined error with Severity 16.
      - Under `sqlcmd -b`, this immediately terminates SQLCMD.
      - If SQLCMD is executed without `-b`, SQLCMD prints error 51000 and attempts to
        send Batches 3 through 64. However, because `SET NOEXEC ON` is already active
        in the session, SQL Server will compile but NEVER EXECUTE any table creation,
        trigger definition, or role seeding!

B. Guard Limitation Identified (Defense-in-Depth Required):
   - Internal script guards verify `DB_NAME() == 'HSWRMS_TEST'`, but CANNOT verify
     which server or host instance is executing the script (e.g. `@@SERVERNAME`).
   - If an operator accidentally connects to an unintended host or remote server
     where a database named `HSWRMS_TEST` also exists, the script-internal guard
     alone cannot prevent execution on that host.
   - Conclusion: Script-internal guards must be coupled with strict client-side
     preflight checks and explicit connection parameters.


4. FAILURE AND PARTIAL-EXECUTION BEHAVIOR ANALYSIS
--------------------------------------------------------------------------------
A. Batch Structure & Transactional Reality:
   - `HSWRMS_TEST_schema.sql` contains 64 separate `GO` batch separators.
   - SQLCMD transmits each batch as an independent TDS request over the network.
   - In SQL Server default mode (`IMPLICIT_TRANSACTIONS OFF`), every batch operates
     under autocommit semantics: statements that succeed in Batch N are committed
     immediately.

B. What `sqlcmd -b` Does and DOES NOT Do:
   - `sqlcmd -b` is a client-side process control flag.
   - When a statement raises an error with Severity > 10:
     * `sqlcmd -b` stops processing and exits with a non-zero exit code.
     * `sqlcmd -b` DOES NOT initiate a transaction rollback on SQL Server.
     * Batches 1 to N-1 that completed successfully REMAIN COMMITTED in the database.
   - Result: If failure occurs on Batch 35, the target database is left in a
     PARTIALLY PROVISIONED STATE (e.g. half the tables exist, half are missing).

C. Safe Recovery Strategy for Partial Execution:
   - Because `HSWRMS_TEST` is a dedicated, isolated test database, attempting complex
     in-place patching or rerunning the script (which would fail on existing objects)
     is prohibited.
   - Prescribed Recovery Procedure:
     1. In case of any execution failure, log the error and halt.
     2. Drop the corrupted test database: `DROP DATABASE [HSWRMS_TEST];`.
     3. Re-create a clean, empty `HSWRMS_TEST` via `provision_hswrms_test.ps1`.
     4. Address the root cause of the DDL failure before retrying.
     5. The primary database `HSWRMS` remains completely untouched.
