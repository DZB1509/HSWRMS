4. MIDWAY FAILURE BEHAVIOR & SAFE RECOVERY PROCEDURES
================================================================================
General Architectural Principle:
  Automatic rollback (such as issuing DROP DATABASE or DROP LOGIN on error) is
  STRONGLY PROHIBITED. Automatic drop logic introduces severe risk of accidental
  data loss if run against unintended targets or misconfigured connections.
  Instead, the script fails closed immediately on error, logs the sanitized fault,
  and allows the operator to execute a safe, idempotent forward-recovery procedure.

Failure Scenarios & Recovery Procedures:

Scenario 1: Pre-Condition Check Fails in Stage 1
  - Example: SQL Server is in Windows-Only mode, or target objects exist without override.
  - Script Action: Aborts immediately with descriptive error before Stage 2.
  - Partial State: ZERO objects created or altered.
  - Recovery: Resolve pre-condition (e.g. enable Mixed Mode) and re-run.

Scenario 2: Database Creation Fails in Stage 2
  - Example: Disk full, insufficient OS file permissions.
  - Script Action: Throws exception, scrubs unmanaged memory, halts.
  - Partial State: Database creation failed; Login and User were NOT created.
  - Recovery: Resolve disk/permission issue and re-run script.

Scenario 3: Login Creation Fails in Stage 3
  - Example: Password does not meet Windows Server password complexity policy.
  - Script Action: Throws exception, scrubs unmanaged memory, halts.
  - Partial State: Database [HSWRMS_TEST] was created; Login and User were NOT created.
  - Recovery Procedure:
    1. Do NOT drop [HSWRMS_TEST].
    2. Operator selects a password meeting complexity policy (upper, lower, digits, symbols).
    3. Operator re-runs script with the authorized database reuse switch:
       .\provision_hswrms_test.ps1 -ServerInstance "localhost" -AllowExistingDb
    4. Stage 1 confirms [HSWRMS_TEST] is ONLINE.
    5. Stage 2 detects database exists and skips creation.
    6. Stage 3 creates the login successfully.
    7. Stage 4 completes user mapping and CONNECT grant.

Scenario 4: User Mapping or Permission Grant Fails in Stage 4
  - Example: Interrupted network connection during database context switch.
  - Script Action: Throws exception, scrubs unmanaged memory, halts.
  - Partial State: Database [HSWRMS_TEST] and Login [hswrms_test_user] exist; User mapping missing.
  - Recovery Procedure:
    1. Do NOT drop database or login.
    2. Operator re-runs script with both reuse switches authorized:
       .\provision_hswrms_test.ps1 -ServerInstance "localhost" -AllowExistingDb -AllowExistingLogin
    3. Stages 2 and 3 skip creation.
    4. Stage 4 maps the user and executes GRANT CONNECT.
    5. Stage 5 verifies effective configuration.
