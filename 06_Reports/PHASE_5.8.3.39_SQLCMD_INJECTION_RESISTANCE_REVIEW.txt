4. TASK 2: INJECTION RESISTANCE & EMPIRICAL TESTING
================================================================================
A. Parser-Only vs. Preprocessed Script Testing:
  1. Parser-Only Isolated Test:
     When an adversarial string such as "test'; PRINT 'INJECTED'; --" was placed into
     a standalone SELECT N'$(TEST_PASSWORD)' without guards, the single quote closed
     the string literal and executed the second statement. This confirmed that raw
     textual substitution into SQL string literals is fundamentally non-parameterized.
  2. Preprocessed Actual Script Test (With Stage 0 Guards and :on error exit):
     When the exact same adversarial input was passed to the actual script structure:
     - Stage 0 ('IF ''$(TEST_PASSWORD)'' = '''' ...') substituted the payload into
       multiple boolean expressions.
     - The single quote immediately produced a compilation syntax error:
       "Msg 156, Level 15: Incorrect syntax near the keyword 'OR'."
       "Msg 102, Level 15: Incorrect syntax near 'END'."
     - Because ':on error exit' is enabled at Line 33, sqlcmd.exe terminated immediately
       with ExitCode 1.
     - The subsequent batches (Stage 1, Stage 2, Stage 3 DDL) were NEVER sent or parsed.
     - The injected statement was NEVER reached or executed.

B. Safe Special Characters vs. Prohibited Characters:
  - Empirical tests confirm:
    * Semicolons (;) inside string literals do NOT terminate the statement.
    * Comment markers (--, /* */) inside string literals do NOT truncate statements.
    * Parentheses () inside string literals do NOT alter T-SQL block structure.
    * Symbols (< > & | ~ @ ^ ! # $ % *) parse cleanly as literal characters.
  - Prohibited Characters:
    * Single Quote ('): Breaks string literal boundaries and triggers syntax errors.
      While :on error exit halts execution, SQL Server's native error message
      (Msg 105/Msg 4145) echoes text "near '...'", risking partial token display.
    * Double Quote ("): Breaks SQLCMD ':setvar' syntax.
    * Macro Sequence ($(): Triggers recursive or unresolved variable resolution.

5. TASK 3: EVALUATION OF SAFER CREDENTIAL PATHS
================================================================================
A. Appropriateness of SQLCMD Textual Substitution:
  - For standard interactive administrative execution in SSMS, SQLCMD textual substitution
    is acceptable and standard practice, PROVIDED that operators strictly adhere to
    the documented password character policy (no single or double quotes).
  - However, relying on syntax errors to halt execution on malformed input is an
    inherent limitation of client-side macro replacement.

B. Hardened Architectural Alternative (Documented in Section 2.E of Guide):
  To provide defense-in-depth and total immunity to delimiter injection, Section 2.E
  specifies a Parameterized RPC Execution Pattern using PowerShell and ADO.NET:
  ```powershell
  $cmd = $conn.CreateCommand()
  $cmd.CommandText = @"
  DECLARE @ddl NVARCHAR(MAX) = N'CREATE LOGIN ' + QUOTENAME(@loginName) + 
                               N' WITH PASSWORD = ' + QUOTENAME(@password, '''') + 
                               N', CHECK_EXPIRATION = OFF, CHECK_POLICY = ON, DEFAULT_DATABASE = ' + QUOTENAME(@dbName) + N';';
  EXEC sys.sp_executesql @ddl;
  "@
  $cmd.Parameters.Add("@loginName", [System.Data.SqlDbType]::NVarChar, 128).Value = "hswrms_test_user"
  $cmd.Parameters.Add("@password", [System.Data.SqlDbType]::NVarChar, 128).Value = $plainPass
  $cmd.Parameters.Add("@dbName", [System.Data.SqlDbType]::NVarChar, 128).Value = "HSWRMS_TEST"
  $cmd.ExecuteNonQuery()
  ```

C. Threat Model & Limitations of Parameterized Alternative:
  - Threat Model & Strengths:
    1. Immunity to Delimiter Breakout: @password is passed as a strongly-typed RPC
       parameter across the TDS wire. It is never spliced into script text.
    2. Native Server-Side Quoting: QUOTENAME(@password, '''') doubles any single quotes
       ('' -> '''') and wraps the string in quotes, guaranteeing the password is treated
       strictly as data.
    3. Zero Secret Echo: Expanded DDL is executed in isolated scope via sp_executesql
       and is never printed to logs or console.
  - Limitations:
    1. Requires a .NET / PowerShell client runner rather than opening a .sql file in SSMS.
    2. Both methods require Windows Authentication with sysadmin or securityadmin privileges.
