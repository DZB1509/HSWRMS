3. STATE-MACHINE AND CANCELLATION-AUDIT FINDINGS
================================================================================
Code and test inspection of `MealOrderServiceImpl.java`, `MealOrderServiceTest.java`,
and `AuditLogService.java` confirmed:

1. Customer Cancellation Restricted to PENDING:
   - Customers can cancel an order only while it is in `PENDING` status.
   - If an order has transitioned to `PREPARING` or `READY`, customer cancellation
     is strictly rejected with `CUSTOMER_CANNOT_CANCEL_PREPARING_ORDER` (400 Bad Request).
   - Proven by unit test `testCancelOrder_CustomerCannotCancelPreparingOrder_ThrowsException`.

2. Staff Cancellation from PREPARING Onward Requires Reason:
   - Authorized F&B staff can cancel an order in `PREPARING` or `READY`.
   - A non-empty cancellation reason is mandatory. If omitted or whitespace-only,
     the service throws `CANCELLATION_REASON_REQUIRED`.
   - Proven by unit tests `testCancelOrder_StaffCanCancelPreparingOrderWithReason`
     and `testCancelOrder_StaffCannotCancelPreparingOrderWithoutReason_ThrowsException`.

3. DELIVERED State is Terminal:
   - Any attempt to cancel or transition an order from `DELIVERED` status throws
     `ORDER_ALREADY_DELIVERED`. It can never be cancelled or rolled back.
   - Proven by unit test `testCancelOrder_AlreadyDelivered_ThrowsException`.

4. Persistent Durable Cancellation Audit:
   - Cancellation audit persistence (introduced in Phase 5.8.3.52) is fully operational.
   - Successful cancellations invoke `auditLogService.record(...)` with:
       * `actorUserId`: logged-in user ID (or CurrentActor)
       * `actorRole`: "CUSTOMER" or "FNB_STAFF" / "MANAGER" / "ADMIN"
       * `action`: "CANCEL_MEAL_ORDER"
       * `targetDataType`: "MealOrder"
       * `targetRefId`: String.valueOf(orderId)
       * `accessStatus`: AuditLogService.SUCCESS
       * `oldValue`: previous status (e.g. "PENDING" or "PREPARING")
       * `newValue`: "CANCELLED; Reason: <cancellation_reason>"
   - Reason is durably recorded in `dbo.AuditLog`, not merely in SLF4J logger.
   - In Phase 5.8.3.53, the audit recording was sequenced prior to entity mutation,
     ensuring complete rollback consistency in POJO unit tests.

5. Folio Non-Charge Guarantee:
   - Cancellation transitions never invoke `postFolioChargeIfEligible`.
   - Cancelled orders never generate Folio charges.

4. FOLIO BILLING AND CHECKOUT FINDINGS
================================================================================
Inspection of `MealOrderServiceImpl.postFolioChargeIfEligible`, `FolioBillingService.java`,
`CheckoutService.java`, and `FnbBillingIntegrationTest.java` confirmed:

1. Strict Settlement at DELIVERED:
   - Charges for `A_LA_CARTE` orders are posted to M5 Folio synchronously when and
     only when the order status transitions to `DELIVERED`.
   - Daily meal selections (`DAILY_MEAL`) are included in retreat packages and
     explicitly bypassed from Folio billing (`CANNOT_CHARGE_INCLUDED_SERVICE`).

2. Authoritative Server Calculation:
   - Item prices are retrieved strictly from `dbo.MenuItem.price` and multiplied by
     `quantity`. Client-supplied totals are completely ignored.

3. Idempotency and Anti-Duplicate Protection:
   - `folioItemRepository.existsBySourceMealOrderId(orderId)` checks for prior postings.
   - If a duplicate delivery transition or network retry occurs, the service logs
     an idempotent return and skips charge posting.
   - Database-level pessimistic write locking on `dbo.MealOrder` (`findByIdWithLock`)
     and `dbo.Folio` (`findByIdForUpdate`) prevents concurrent posting races.

4. Transactional Integrity:
   - Billing exceptions are never swallowed. If Folio posting fails, the exception
     rolls back the transaction, preventing the order from falsely showing `DELIVERED`.

5. Checkout Guard Interaction:
   - `FolioBillingService.validateBillingGuard(retreatBookingId)` queries
     `mealOrderRepository.findUnsettledOrdersForBooking(retreatBookingId)`.
   - If any order remains in `PENDING`, `PREPARING`, or `READY`, it throws
     `UNSETTLED_SERVICE_ORDERS`, blocking draft invoice generation, payment processing,
     and checkout finalization in `CheckoutService.processPayment`.
   - Checkout is permitted only when all dining orders are settled (`DELIVERED`)
     or `CANCELLED`.

6. FRONTEND API WIRING AND KDS POLLING FINDINGS
================================================================================
Inspection of `fnbApi.ts`, `DiningContext.tsx`, `useKdsPolling.ts`, `FnbDashboardPage.tsx`,
`MealPrepListPage.tsx`, `MealOrderDetailPage.tsx`, `DailyMealSelectionPage.tsx`,
and `AlaCarteOrderPage.tsx` revealed:

1. Resolved Defect in `fnbApi.ts`:
   - Observed Defect: `fnbApi.updateKdsOrderStatus` called `apiClient.put(...)`,
     whereas backend `FnbKdsController.java` maps `@PatchMapping("/orders/{id}/status")`.
   - Resolution Applied: Corrected `apiClient.put` to `apiClient.patch` in `fnbApi.ts`.
   - Status: RESOLVED and verified via `npm run build` (tsc -b && vite build).

2. KDS Polling Architecture (`useKdsPolling.ts`):
   - Interval: Default 12,000 ms (12 seconds), within the required 10–15s window.
   - Overlap Prevention: Uses `inFlightRef.current` to block overlapping polls.
   - Tab Visibility: Pauses timer when document is hidden; triggers immediate poll
     when tab becomes visible.
   - Lifecycle Cleanup: Cancels interval and sets `isMountedRef.current = false`
     upon component unmount to prevent memory leaks.
   - Manual Refresh: `manualRefresh()` triggers an immediate poll with animated
     `isManualRefreshing` spinner and button disable guard.

3. Flow Tracing from UI to Backend:
   - `FnbDashboardPage`: Fetches live KPIs via `fnbApi.getKdsDashboardKpis('2026-09-24')`
     and syncs active kitchen queue. Fallback to local queue on network error.
   - `MealPrepListPage`: Renders paginated queue with status and dietary filters.
     Status updates call `DiningContext.updateFulfillmentStatus`, which invokes
     `fnbApi.updateKdsOrderStatus`. Cancellation prompts for mandatory reason and
     calls `fnbApi.cancelKdsOrder`.
   - `MealOrderDetailPage`: Queries `fnbApi.getKdsOrderDetail(numId)` when navigating
     directly to an order ID.
   - `DailyMealSelectionPage`: Submits via `fnbApi.createDailyMealOrder`.
   - `AlaCarteOrderPage`: Submits via `fnbApi.createAlaCarteOrder`. Server calculates
     line totals and total amounts authoritatively.

[Finding 1 - P1 Integration Gap (Deferred to Phase 5.9)]:
  - Description: Boundary ports (`BookingContextPort`, `DietaryProfilePort`) are
    fully implemented and tested in `m4fnb/integration`, but are not yet injected
    into `MealOrderServiceImpl`. Consequently, order placement does not enforce
    `isCurrentlyActive(orderDate)`.
  - Risk: An authenticated customer with a valid past or future booking could place
    an order outside their active stay dates.
  - Action: Inject `BookingContextPort` and `DietaryProfilePort` into `MealOrderServiceImpl`
    in Phase 5.9.

[Finding 2 - P1 Defect (RESOLVED in Phase 5.8.3.54)]:
  - Description: `fnbApi.updateKdsOrderStatus` used HTTP `PUT` instead of `PATCH`,
    causing `405 Method Not Allowed` against `FnbKdsController.@PatchMapping`.
  - Action: Corrected `apiClient.put` to `apiClient.patch` in `fnbApi.ts`.
  - Status: RESOLVED and verified.

[Finding 3 - P2 Prototype Decoupling (Documented Risk)]:
  - Description: Frontend customer ordering pages (`DailyMealSelectionPage.tsx`,
    `AlaCarteOrderPage.tsx`) fall back to prototype identifier `'usr-cust-01'`
    when `profile.id` is not loaded in `CustomerContext`.
  - Risk: Low in production because JWT authentication attaches the real user ID
    to requests and the backend verifies ownership against the database.
  - Action: Documented for end-to-end integration testing in Phase 5.9.

[Finding 4 - P2 Unresolved Package F&B Plan Policy (Blocker)]:
  - Description: Workspace B's hardcoded 8 retreat package plans were rejected.
    Whether package meal allowances are advisory or strict gates remains an
    unresolved business decision requiring Product Owner approval.
