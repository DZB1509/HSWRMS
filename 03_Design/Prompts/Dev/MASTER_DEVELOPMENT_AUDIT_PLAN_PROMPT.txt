5. APPROVED BUSINESS CORRECTIONS
==================================================

These decisions OVERRIDE outdated frontend prototype behavior and any conflicting old wording.

------------------------------
M1 — IDENTITY / HEALTH
------------------------------

Separate:
- USER identity/authentication
- CUSTOMER_PROFILE
- HEALTH_PROFILE

Sensitive data uses minimum-necessary projection.

F&B Staff:
- allergy/dietary information only.

Therapist:
- treatment-safety information relevant to assigned session only.

Receptionist:
- must not receive unrestricted health information.

Consent is required for storing/maintaining applicable health data.

Health deletion request may be Deferred/Pending when an active/upcoming retreat still requires the data.

------------------------------
M2 — RETREAT / ACCOMMODATION
------------------------------

RetreatBooking is the stay context used by M3/M4/M5.

Villa Category != Physical Villa.

Customer selects category as part of booking.
Physical Villa is the operational resource assigned for stay/check-in.

Walk-in/offline booking reuses S15.
Do not create a separate Walk-in screen.

Booking/payment concurrency must eventually be protected by backend transaction logic,
not frontend availability alone.

------------------------------
M3 — SPA / THERAPY
------------------------------

THIS IS A CRITICAL CORRECTION.

M3 is SYSTEM-DRIVEN scheduling.

Customer or Receptionist provides:
- treatment;
- preferred date/time constraints;
- optional note/flexibility.

Customer/Receptionist MUST NOT independently pick Therapist and Treatment Room in the normal flow.

A generated schedule candidate is one indivisible combination:

Time Slot
+ Qualified Therapist/Yoga Instructor
+ Compatible Treatment Room

S27 shows system-generated complete candidates.

Candidate generation DOES NOT reserve resources.

On S28 final confirmation:
- revalidate the complete candidate;
- reserve Therapist + Treatment Room atomically;
- if either resource fails validation, commit neither resource;
- regenerate/reload alternatives.

Production backend must use a transaction and appropriate SQL Server/JPA locking/concurrency control.
Do not claim frontend JavaScript provides atomic reservation.

Session lifecycle:

session_status:
- SCHEDULED
- RESCHEDULING
- CANCELLED
- COMPLETED
- NO_SHOW

Attendance confirmation lifecycle is SEPARATE:

confirmation_status:
- PENDING
- CONFIRMED
- DECLINED
- EXPIRED

IMPORTANT:
CUSTOMER_CONFIRMED is NOT an approved session_status.

If Customer confirms attendance:
session_status remains SCHEDULED
confirmation_status becomes CONFIRMED.

IN_PROGRESS is NOT an approved persisted SpaSession status unless explicitly approved later.

Reminder timeline:
- T-24h informational reminder
- T-2h confirmation request
- T-75m final reminder if still pending
- T-60m response deadline
- T-15m upcoming-session reminder

At T-60m if confirmation is still PENDING:
confirmation_status → EXPIRED
session_status → RESCHEDULING
invoke recovery.

EXPIRED != NO_SHOW.

Recovery order:
1. preserve same session time and replace unavailable Therapist/Room;
2. if session time changes, explicit Customer consent is required;
3. slot swap is last resort and all affected Customers must consent;
4. resources must be revalidated before commit.

Therapist final fulfillment action:
- COMPLETED
or
- NO_SHOW

Extra Spa uses the same scheduling engine.

The exact M3/M4 → M5 Folio posting ownership remains an Open Item.
Do not silently hard-wire a module ownership decision.

------------------------------
M4 — DIETARY F&B
------------------------------

M4 is not only order CRUD.

It includes:
- personalized menu;
- ingredient batches;
- recipe quantity;
- menu availability;
- meal fulfillment;
- inventory usage;
- extra a-la-carte charge traceability.

MENU_ITEM ↔ INGREDIENT is M:N through:

MENU_ITEM_INGREDIENT

It stores the recipe quantity per serving.

Business calculation:

required ingredient quantity
=
quantity_per_serving × ordered_servings

Usable stock must consider:
- remaining quantity;
- expiration;
- stock condition.

Do NOT treat expired/unusable stock as available.

F&B Dashboard hierarchy should support:

KPI Summary
→ Today's Meal Orders
→ Ingredient Demand + Inventory Alerts
→ Menu Availability

Ingredient Demand is operational data, NOT a catalog.

No new official screen is required for this feature.

Recipe definition may be incorporated into existing Menu Item management.
Ingredient demand/shortage belongs on F&B Dashboard.

Inventory consumption/reservation must use backend transactional validation when implemented.

------------------------------
M5 — FOLIO / PAYMENT / CHECKOUT
------------------------------

Folio is a running stay account.

Invoice is the formal consolidated billing result.

PaymentTransaction records payment activity.

Payment Successful != Checkout Completed.

Final checkout requires correct finalization of:
- applicable service states;
- Folio;
- Invoice;
- Payment;
- RetreatBooking;
- PhysicalVilla operational state.

If Spa/F&B service remains unresolved:
checkout must be blocked until resolved according to approved rules.

Payment callbacks must be idempotent.
Duplicate provider callbacks must not:
- double charge;
- create duplicate payment;
- close Folio twice;
- finalize stay twice.

M2 deposit vs M5 final payment ownership remains an Open Item.
Supported CASH vs VNPay scope may also remain open if current SRS has not resolved it.

Do not silently decide an unresolved scope.

------------------------------
M6 — ADMIN / PERMISSIONS
------------------------------

Backend authorization is mandatory.

Hiding a menu/button is NOT security.

Use:
- roles;
- permissions;
- Spring Security;
- JWT;
- backend authorization checks.

Manager != Admin.

Limited delegation:
- temporary;
- scope-limited;
- time-bounded;
- cannot grant protected core admin powers.

Audit records must be treated as immutable through business UI.

Feature flags must not disable protected core rules such as:
- RBAC;
- audit logging;
- checkout/payment guard.
